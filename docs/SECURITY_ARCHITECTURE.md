# Security Architecture

## Core Security Principles

- **Least privilege:** Components only have the permissions they strictly need.
- **Server-side authorization:** Backend enforces tenant/entitlement checks, not the desktop client.
- **Tenant isolation:** Strict logical separation based on the verified Firebase UID.
- **No plaintext passwords:** Firebase Auth manages user credentials.
- **No secrets in renderer:** Renderer only sends commands, processes UI.
- **No Firebase Admin credentials in desktop application:** The desktop app uses Firebase Client SDKs only. Privileged Admin operations belong strictly to the Vercel Server Functions backend.
- **Secure Electron IPC:** ContextBridge and strict channel validation. No arbitrary code execution.
- **Input validation:** All inputs validated at the boundary (Main process).
- **Parameterized SQL:** Strictly enforced to prevent SQL injection.
- **Encrypted backups:** SQLite file encrypted before upload.
- **Protected private keys:** Windows DPAPI through Electron `safeStorage` asynchronous APIs for cryptographic identity (Ed25519). The private key never leaves the Windows installation, never enters Firestore, never enters renderer JavaScript, never enters logs, and must not be stored as plaintext. TPM is optional.
- **Audit logs for privileged actions:** Tracked on the backend for sensitive changes.

## Copy Protection Requirements

The architecture must prevent a normal customer from simply bypassing the single-PC license.
Tests that MUST fail to authorize production access:

1. Copying the `.exe` to another PC.
2. Copying the `.exe` and the user credentials to another PC.
3. Copying the `.exe` + credentials + the entire SQLite database to another PC.
4. Copying the entire application folder to another PC.

The copied installation MUST fail installation authorization because it does not possess the authorized installation's private key, which is securely bound to the original Windows machine's credential manager/key storage. Additionally, an attacker who steals Firebase credentials cannot register their own unauthorized machine because registration strictly requires a one-time, out-of-band activation code.

_(Note: PHASE 3.5 implements the complete end-to-end cryptographic installation activation using the Ed25519 private key in the Main process and a secure 32-byte challenge generated by the backend.)_
