# End-to-End Installation Activation (Phase 3.5)

This document describes the complete lifecycle of a NovoPharma Desktop application installation. The lifecycle uses a combination of Firebase Authentication, Ed25519 local cryptographic identity, and Vercel server-side validation to securely bind an installation to a tenant.

## 1. Registration (`PENDING_APPROVAL`)

When the user signs in to the desktop app for the first time, the desktop requires an **Activation Code** generated by the Super Admin.
The desktop application:

1. Generates an Ed25519 key pair locally and encrypts the private key via Windows DPAPI / Electron `safeStorage`.
2. Sends the `activationCode`, `installationId`, and `publicKey` to the Vercel backend.
3. The Vercel backend hashes the activation code, confirms it matches a valid one-time provisioning slot, and registers the `publicKey`.
4. The desktop transitions to the `WAITING_FOR_APPROVAL` state (API responds with `PENDING_APPROVAL`). The activation code is permanently consumed.

## 2. Super Admin Approval (`APPROVED`)

A human Super Admin must log into the Super Admin portal, verify the public key fingerprint, and explicitly approve the installation.
Approving the installation changes the public key status to `APPROVED`.
**Important**: `APPROVED` does NOT mean `ACTIVE`. It simply authorizes the desktop to request an activation challenge.

## 3. Cryptographic Activation (`ACTIVE`)

Once approved, the desktop app asks the backend to activate the installation.

1. **Challenge Request**: The desktop requests a challenge for its `installationId`. The backend generates a 32-byte cryptographic challenge that expires in 5 minutes.
2. **Canonical Payload Signing**: The desktop creates the canonical payload:
   `NOVOPHARMA-ACTIVATION-V1\n<challengeId>\n<challenge>\n<installationId>`
   The desktop signs this payload using its locally stored Ed25519 private key.
3. **Completion**: The desktop sends the signature to the backend. The backend verifies the signature against the `APPROVED` public key.
4. **Activation Transaction**: If the signature is valid and no other computer is actively occupying the slot, the backend atomically sets the installation as `ACTIVE`.

## Renderer Isolation Boundary

The UI (Renderer process) is completely isolated from sensitive cryptographic operations:

- The Renderer **never** accesses the Firebase ID token or UID.
- The Renderer **never** accesses the `tenantId`.
- The Renderer **never** accesses the `private_key` or handles the raw `challenge` payload.
- The Renderer can only send generic instructions (like `api:activation:activate` or `api:activation:registerKey`) and receives safe UI-friendly strings and statuses in return.

## Retry and Expiration Policies

- Challenges expire in exactly 5 minutes. If a challenge expires (`410 Gone`), the desktop gracefully discards it and fetches a new challenge.
- Network failures allow for seamless retries without recreating the underlying cryptographic identity.
- Single-active-slot violations (`409 Conflict`) require the Super Admin to revoke the existing computer first.
